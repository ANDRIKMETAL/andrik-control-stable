R702 ROOT CAUSE + LOCAL INTEGRATION TEST

Confirmed root cause from R701 source:
- Old cache-clean temporary output name: <hash>.mp3.clean-<pid>-<time>-<attempt>
- FFmpeg could not infer an output muxer from that suffix and exited with code 234:
  "Unable to choose an output format ... use a standard extension or specify the format manually."
- That made fresh MP3 cache jobs fail. The radio loop then skipped MP3 items and eventually returned to video clips, matching the observed behavior.

R702 fix:
- cache-clean temp ends in .mp3
- explicit -f mp3

Integration test performed locally with:
- 2 MP3 tracks
- 1 video clip whose VIDEO stream is 3 s but AUDIO/container is 6 s (deliberate last-frame-freeze case)
- persistent master + normal visual + clip feeder + PCM audio

Observed across two complete clip handoffs:
- MP3 cache failures: 0
- clip -> next MP3 handoff: 7 ms, then 5 ms
- title/current changed from clip to next MP3
- producerRunning returned true on next MP3
- clip final frame did not wait for the 6 s container duration
- cached MP3 files were valid and > 256 KiB
